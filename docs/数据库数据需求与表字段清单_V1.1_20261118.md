# 新能源项目收益预测器：数据库数据需求与表字段清单

版本 V1.1 · 2026-11-18 · 开发接手复核稿

**首期建议建 28 张物理表。** 这份基线按单所有者、保留现有结算电量入口和新旧项目数据、使用标明为模拟的现货价格跑通业务来设计。其余 10 项中，2 项首期并入已有表，4 项先派生，4 项按外部数据或产品功能启用。完整编号、落点和启用条件见第 3 节。

**首期业务验收可以离线完成。** 项目、电量、六项未来供需假设、收益参数由客户配置或导入，现货价格使用固定演示数据。真实历史现货行情是外部数据接入阶段的第一项。若首期合同要求以真实或外部给定价格出具收益结果，应提前安排第 9.1 节的价格接入工作。

**正式预测流程的验收条件**为后台算法实际读取冻结的全周期小时供需，返回可校验的价格曲线，前台采用后再用该版本做基准收益测算与交叉验证。提交、回传、采用及异常验收见 [现货预测后台算法对接规格](现货预测后台算法对接规格_V1.0.md)。

## 1. 这份清单解决什么问题

软件需要保存四类数据：**客户填写的项目与测算参数、外部取得的市场数据、计算生成的数据、支持历史复现的版本与来源记录**。只把页面上的输入框搬进数据库，无法保证旧项目、粗算快照和基准结果在修改后仍可核对。

本文件以当前本地代码为依据，覆盖“项目创建 → 结算电量配置 → 项目电价粗算 → 现货电价预测（含供需配置）→ 收益参数补充与细化 → 基准结果 → 交叉验证”。“精算”继续指现货预测与收益参数细化共同形成的测算过程，不新增一个独立业务模块。

本文给出的是**逻辑表及字段需求**，不是已经建成的数据库，也不是最终 SQL。开发可以将明确标为派生的数据做成视图、缓存或文件，将小型结构化草稿存成有固定契约的 JSON；不能因此丢失版本关系或业务含义。

### 1.1 必须区分的两种完成程度

|完成程度|需要具备什么|当前情况|
|---|---|---|
|接库后运行现有业务流程|项目、参数、曲线、版本、计算结果、权限与保存接口|本文件可作为开发起点；当前仍以浏览器本地存储为主|
|使用真实数据开展价格预测|真实历史数据、选定算法及其所需特征、训练或求解过程、可核查的评价|尚未全部具备，来源、算法及验收口径见第 9 节|

现有历史分析中存在 `sourceType="database"`、同时 `mock=true` 的数据；当前 LSTM、XGBoost、Ensemble 及部分质量指标仍为演示生成。新增供需配置已能生成并冻结输入，但演示价格模型尚未使用这些供需特征定价。**建库、供需数据齐全和真实预测模型可用，是三个不同的交付条件。**

### 1.2 客户需要提供什么

|业务环节|客户或数据服务方提供|系统自动取得或生成|
|---|---|---|
|项目创建|名称、区域、类型、容量、起始年、年限、配储边界|项目 ID、时间、权限|
|结算电量|选择一种电量配置方式，提供对应年利用小时或小时曲线|继承项目容量与周期，生成年度和小时电量|
|项目电价粗算|预期现货均价节点、捕获率，以及截至此步仍未填写的共用收益参数|继承此前已填参数，保存当时的粗算快照|
|供需配置|六元素首年总电量、后续逐年增长率、分月与分时权重|继承测算周期，归一化权重，展开全周期小时数据|
|现货预测|首期演示使用系统样例；真实数据阶段由数据服务方提供，客户补充模型需要的情景假设|运行、价格曲线、质量指标、输入版本关系|
|收益参数补充与细化|核对默认值和历史待确认项，细化交易策略、环境价值、费用等|继承已确认参数；保留原粗算快照|
|基准结果与交叉验证|选择明确的结果版本、必要时调整提示阈值|收入结果、粗算与基准差异及提示|

客户无需手填结果表、小时派生表、版本表和审计表。数据库中表较多，不代表页面要增加同样多的录入步骤。

## 2. 全库统一约定

### 2.1 字段、单位与空值

|约定|要求|
|---|---|
|类型|`ID` 唯一标识；`Text` 文本/枚举；`Int` 整数；`Decimal` 精确数值；`Bool` 布尔；`DateTime` 带时区时间；`JSON` 有 schema 的结构化对象|
|单位|电量 MWh；功率 MW；价格/折合收益单价 元/MWh；金额 元；等效利用小时 h|
|比例|名称以 `_ratio` 结尾的字段用小数表达，例如0.2表示20%；分配/兑现比例限0—1，增长率、差异率按各自范围约束。差异率可以为负或大于1|
|百分数|名称以 `_pct` 结尾的字段以百分数保存，例如增长率 5 表示 5%；粗算捕获率 95 表示 95%；偏差阈值 10 表示 10%|
|正负|电价、策略损益、机制差价、联络线净值、剩余需求可为负；普通供需总量、权重、当前费用输入不得为负|
|空值|`NULL` 表示未知/未填，不得自动改成 0；不适用、默认待确认、历史来源未知分别有状态表达|
|精度|保存计算原始精度；页面和导出的四舍五入只影响展示。具体 Decimal 位数按最大容量、年限和误差测试确定，不直接截断旧数据|
|必填|表中“必填”指提交有效配置/完成运行时的要求；编辑草稿可暂缺。历史迁移缺项允许保留，但必须标记不可验证，不能补造事实|
|时间|审计时间保存带时区时间；业务日历和数据时区单独声明。市场区域当前默认按 Asia/Shanghai，未来按区域配置|
|字典|枚举代码稳定，中文标签单独展示；不以中文名称代替主键|

**模型日历与真实日历必须分开：**当前电量、供需与预测采用固定 365 天模型年，8760 个小时或 35040 个 15 分钟时段；2028 模型年同样为 365 天。月份天数固定为31/28/31/30/31/30/31/31/30/31/30/31。真实历史数据使用真实时间戳，保留闰日。真实历史进入模型时的闰日映射、缺失处理、时间聚合都必须记录方法版本，不能让自然日期库自动为模型序号插入闰日。

### 2.2 通用列组

下文引用列组时，这些列均属于该表；复合主键明细表不强制再加无意义的自增 ID。

|列组|字段|约束|
|---|---|---|
|A：记录审计|`created_at:DateTime`、`created_by:ID?`、`updated_at:DateTime`、`updated_by:ID?`|用户 ID 关联用户表；历史未知操作者为空并保留迁移批次|
|V：配置版本|`version_no:Int`、`parent_version_id:ID?`、`schema_version:Text`、`status:Text`、`content_hash:Text`、`sealed_at:DateTime?`、`change_reason:Text?`|状态至少 draft/sealed；已封存版本不原地改业务值；子版本另建。继承 A|
|R：计算执行|`execution_status:Text`、`requested_at/started_at/completed_at:DateTime?`、`requested_by:ID?`、`algorithm_version:Text`、`input_hash:Text`、`output_hash:Text?`、`error_code/error_message:Text?`、`idempotency_key:Text`|queued/running/succeeded/failed；完成后输入输出不可改；重试/重算产生独立执行 ID，幂等键防重复提交|

“已封存”只表示该版本不可变，**不代表所有参数经客户确认**。锁定场景也不等于确认默认值。

哈希分两种用途：配置业务 `content_hash`、运行业务 `input_hash/context_fingerprint` 只覆盖实际计算值、模式、适用边界、固定价量数据及规则版本；确认状态、审计时间、页面状态不参与。确认同值时，即使增加了配置/确认记录，也应按业务内容判定原计算仍然有效。`payload_hash` 对完整历史对象校验，用于保真，不能拿它代替业务过期判断。动态的“与当前输入是否一致”通过当前状态核对并展示，不回写成功运行的原始输入与输出。

### 2.3 版本关系

```text
当时项目边界 + 电量版本 + 共用收益配置 + 粗算草稿
  → 粗算输入快照 → 粗算快照及年度结果

当时项目边界 + 已封存供需版本 + 生成清单
  → 预测输入快照 → 现货预测运行及价格

当时项目边界 + 电量版本 + 场景收益配置 + 指定预测运行
  → 收益输入快照 → 基准收益运行及年度结果

选定粗算快照 + 总览中的基准收益运行 + 提示阈值
  → 交叉验证页面及导出
```

`input_snapshot` 冻结项目边界及各输入版本引用，不另要求建立一套重复的“全项目版本表”。项目表上的当前指针用于继续编辑；历史结果始终读取运行绑定的版本。图中的输入引用按用途选择，粗算不要求先有供需配置或预测结果。

### 3.2 核对出的缺项与重复

|发现|首期修订|
|---|---|
|外部数据来源主表推迟后，导入批次仍需要能证明来源|第07表增加来源类型、名称、标识/引用及导入幂等键。第05、09表未启用时，相关版本外键可空，批次来源与种子模板标识仍保存|
|旧项目恢复缺少逐项版本映射和失败处理字段|第07表补原备份校验和、对象类型及旧ID到新ID的映射、失败报告。原始备份和映射可保存在第06表登记的文件；历史快照内部原ID保留|
|供需生成记录、小时数据和典型曲线有重复持久化风险|第15表保存紧凑配置及一次生成清单。第21表视需要缓存展开。第11表以源值为原始数据，归一化份额仅为固定算法产物；历史只有权重时以现存权重为迁移权威|
|同一电量和价格有两个手工维护入口的风险|第13表存客户填的年度利用小时，第14表直接导入时以原始小时值为准，年度量由汇总生成。第24表只写原生价格，小时均价按版本聚合|
|当前生效预测在项目与衔接配置重复维护；收益运行对价格也重复引用|项目当前指针为生效预测的唯一入口；历史收益以第08表绑定的预测为准。兼容字段查询时派生；若为索引冗余，提交时校验同值|
|同一组年度结果在明细表、归档 JSON 和交叉验证重复存储|第32、34表是新结果的年度查询来源，归档 JSON 用于原始快照保真。首期交叉验证使用这两张年表及固定ID，阈值只影响提示|
|比较 CSV 缺少足以复查的统一引用|导出同时写入粗算快照ID、基准收益运行ID、实际阈值和比较规则版本；只有双方明确且可比时导出成功对照|
|模拟现货历史与外部预测曲线用途容易混用|历史与预测各有时间口径、来源和入口；如外部提供未来价格曲线，按第9.1节单独扩展第23、24表的接入方式|
|同一张手工年表可同时包含导入值、自动展开值和人工改动|第29表允许 `mixed` 并记录已知单元格来源。客户仍按整表确认|
|部分旧快照及结果没有完整输入版本；强行填外键会篡改历史含义|第31、33表明确迁移例外，显式记录来源未知。结构化行从原对象抽取，历史源文件与快照校验和分别核对|

### 3.3 首期建表与接线顺序

|顺序|物理表编号|验收节点|
|---|---|---|
|1. 账号、项目、导入和来源|01、02、03、06、07、08、38，共7张|账号隔离，新建项目，上传可追溯文件，恢复旧备份|
|2. 结算电量|10–14，共5张|直接小时曲线，或年度利用小时加典型曲线，得到同一口径的结算电量|
|3. 粗算与收益配置|26–32，共7张|建立默认基准场景，参数共用，生成原粗算，默认值及手工年表可核对|
|4. 供需与演示预测|15–19、23、24，共7张|六元素供需总量守恒，演示价格可生成、切换并追溯版本|
|5. 基准收益及交叉验证|33、34，共2张|生成基准年结果，对照并导出，单年改费重算时原粗算仍可核对|

这些分组用于实现顺序。数据库迁移脚本可先声明所有表，再配置跨组外键。新建项目时，先以空值建立项目/场景的当前指针，写入各子版本后在同一事务内更新对应指针。失败时旧的有效版本继续可读。

第05、09、20表及第8节扩展表未启用时，首期迁移脚本不声明指向这些表的外键。首期有替代来源字段的，继续保留对应来源内容。其余条件字段随功能迁移一并增加约束。

原有省份政策资料面板、外观和筛选偏好、打印及导出按钮可沿用固定资料或应用状态。政策库编辑、发布和集团级权限另立需求；实际参与计算的依据照常写入参数来源和快照。

## 5. 结算电量与供需表

### 10 `energy_profile_version`：典型发电曲线版本

粒度：曲线版本 × 模型小时。主键 `(profile_version_id,hour_index)`。

|字段|类型|含义与约束|
|---|---|---|
|`profile_version_id`、`hour_index`|ID、Int|曲线版本，小时序号 1—8760|
|`raw_value`|Decimal?|客户原始曲线值，≥0；新导入必留，旧数据无原始幅值可空|
|`raw_value_status`|Text|original/legacy_unavailable，区分真实原值与历史无法取得|
|`normalized_share`|Decimal|派生权重，≥0、全年和为 1；不可独立编辑|
|`source_row_no`|Int?|源行号，方便定位错误|

新导入不得只保留归一化后的值而丢失客户原始值。当前历史项目可能只存归一化曲线；迁移时保留该曲线不变，原始幅值标未知，不能把权重伪装成原值或自行逆推。未获得真实曲线时，示例/均分曲线应明确标为假设。

### 12 `energy_input_version`：结算电量配置版本

粒度：项目的一次电量配置。主键 `id`。四种配置方式均应支持。

|字段|类型|含义与约束|
|---|---|---|
|`id`、`project_id`|ID|标识、项目|
|`input_mode`|Text|`hourly_8760` / `annual_hours` / `typical_curve_8760` / `province_typical_curve`|
|`start_year`、`forecast_years`、`capacity_mw_snapshot`|Int、Int、Decimal|从项目取得并记录适用边界，不重复让客户填写|
|`profile_version_id`|ID?|采用的典型曲线；需形状时引用明确版本|
|`source_batch_id`|ID?|输入批次|
|`calendar_type`、`interval_minutes`|Text、Int|当前固定365天、60分钟|
|`generation_method`、`generator_version`、`generation_parameters_json`、`validation_report_json`|Text、Text、JSON、JSON|展开方法、种子/年度形状等实际生成参数、校验结果；历史演示生成曲线也须明确来源|
|V|通用列组|版本及封存状态|

年度利用小时、容量、典型形状可以生成小时电量，不再要求客户同时填一份年度 MWh。小时直接导入时，年度电量由小时汇总。禁止两套可编辑总量互相冲突。

只有年度利用小时而没有小时形状时，可以形成年度总量，不能据此声称已有真实小时数据。当前新流程须配齐典型曲线或直接导入小时数据才能完成小时收益测算；迁移已有演示展开曲线时保留其实际值和生成依据，不能重新生成并替换旧曲线。

### 13 `energy_annual_input`：年度利用小时输入

|字段|类型|含义与约束|
|---|---|---|
|`energy_version_id`、`year`|ID、Int|版本、测算年份|
|`annual_hours_h`|Decimal|年度等效利用小时；当前导入要求 >0；各年覆盖完整|

### 14 `energy_hour_value`：小时结算电量

粒度：电量版本 × 年 × 小时。主键 `(energy_version_id,year,hour_index)`。

|字段|类型|含义与约束|

直接导入模式保留原始输入及来源；生成模式可不逐行落库而按版本生成缓存。`month/day/hour` 可按模型日历派生，不使用自然闰年时间戳替代模型序号。

|---|---|---|
|`id`、`project_id`|ID|标识、项目|
|`province_code`、`market_area_id`、`start_year`、`forecast_years`|Text、ID、Int、Int|配置时项目边界；从项目取得|
|`tie_line_mode`|Text|net 单向净额 / bidirectional 双向分别配置|
|`calendar_type`、`interval_minutes`|Text、Int|fixed_365_days、60；每年8760小时|
|`curve_reuse_mode`|Text|当前 same_shape_across_years，跨年复用典型形状|
|`row_version`|Int|编辑并发保护|
|`pending_input_json`|JSON?|若支持刷新恢复，保存尚未应用的批量文本，不能进入正式计算；不提供服务端恢复时留浏览器临时态|
|`generation_manifest_json`|JSON?|首期合并第20表。封存时写生成器版本、时间、输入及输出校验和、日历、点数、误差、年度摘要及可选文件引用|
|`validation_report_json`|JSON?|校验结果|
|V|通用列组|draft 可编辑；sealed 不可改。版本号按项目唯一|

完整配置由 16—19 表重建；可生成只读配置 JSON 供算法传输，但不能另设一个与子表互相漂移的可编辑副本。切换联络线模式保留不活动分支。项目改起始年/年限后，旧配置保留但需要显式复核，不能重新解释旧首年电量。

首期每个封存版本绑定一份生成清单。生成器版本改变时创建新供需版本，旧运行仍引用旧清单；同一配置将来需要并行保留多套生成器产物时再启用第20表。

### 16 `supply_series`：供需元素起点与方向

粒度：供需版本 × 元素 × 方向。主键 `id`；唯一键 `(supply_version_id,element_code,direction_code)`。

|字段|类型|含义与约束|
|---|---|---|
|`id`、`supply_version_id`|ID|标识、版本|
|`element_code`|Text|`load` 省内负荷、`tieLine` 联络线负荷、`wind` 风电、`solar` 光伏、`hydro` 水电、`nonMarket` 非市场化|
|`direction_code`|Text|普通元素 none；联络线 net/export/import|
|`base_energy_mwh`|Decimal?|首个测算年的总电量。普通元素及 export/import ≥0；net 可正可负；活动分支必填，显式 0 合法|
|`input_origin`、`source_batch_id`、`note`|Text、ID?、Text?|manual/import/template 等来源|

net 正数送出、负数受入；双向模式按 export－import 计算净值。不活动分支允许缺项。非市场化出力保持可自由配置的独立元素，不要求拆分组成。

### 17 `supply_growth_rate`：逐年增长率

粒度：元素分支 × 后续年份。主键 `(series_id,year)`。

|字段|类型|含义与约束|
|---|---|---|
|`series_id`、`year`|ID、Int|元素分支、测算第二年至末年|
|`growth_rate_pct`|Decimal|增长率百分数，≥－100；每个后续年显式填写，零量系列也不自动补 0|
|`source_batch_id`|ID?|导入来源|

`E_y = E_(y-1) × (1 + growth_rate_pct / 100)`。首年不应用增长率。净额模式下非负增长因子保持原有方向；要表达同年双向流动使用双向模式。

### 18 `supply_month_weight`：典型年分月权重

粒度：元素分支 × 月。主键 `(series_id,month_no)`。

|字段|类型|含义与约束|
|---|---|---|
|`series_id`、`month_no`|ID、Int|分支、1—12月|
|`raw_weight`|Decimal?|非负相对权重，无单位；保留客户原值，不要求合计100|
|`source_batch_id`|ID?|来源|

非零电量的活动系列须12项完整且总和>0；显式零电量系列允许无用曲线缺省。归一化份额只派生，不作为第二套输入。

### 19 `supply_hour_weight`：每月典型日分时权重

粒度：元素分支 × 月 × 日内小时。主键 `(series_id,month_no,hour_of_day)`。

|字段|类型|含义与约束|
|---|---|---|
|`series_id`、`month_no`、`hour_of_day`|ID、Int、Int|分支、1—12月、0—23时|
|`raw_weight`|Decimal?|非负相对权重；保留原值|
|`source_batch_id`|ID?|来源|

有电量的月份必须24项完整且总和>0；无电量月份允许无用曲线未填或全零。每元素每年使用12条典型日形状，当前不要求每年重填288项。

### 20 `supply_generation`：小时数据生成记录

粒度：供需版本 × 生成器版本的一次成功生成。首期作为第15表内部生成清单。以后单独建表时使用以下字段，主键 `id`。

|字段|类型|含义与约束|
|---|---|---|
|`id`、`supply_version_id`|ID|生成标识、已封存配置|
|`generator_version`、`input_hash`、`output_hash`|Text|方法与输入输出校验|
|`generated_at`、`calendar_type`、`interval_minutes`|DateTime、Text、Int|生成时间及口径|
|`annual_summary_json`|JSON|各年六元素、送出/受入、剩余需求的 MWh 汇总；可由小时数据重建|
|`expected_point_count`、`actual_point_count`|Int|按“年份×小时×已输出元素”计数；保存计数口径|
|`conservation_status`、`max_error_mwh`|Text、Decimal|总量守恒检查与最大误差|
|`artifact_file_id`|ID?|小时数据改用文件存储时的文件引用|

小时展开公式：`月电量 = 年电量 × 月权重 / 全年月权重和`；`典型小时电量 = 月电量 / 月天数 × 小时权重 / 该月24小时权重和`。再按当月每天重复展开。年度、月度、288个典型小时、8760小时不得作为四套独立可编辑数据。

### 21 `supply_hour_value`：供需小时数据（可派生）

粒度：生成记录 × 年 × 小时 × 元素。主键 `(generation_id,year,hour_index,element_code)`。

|字段|类型|含义与约束|
|---|---|---|
|`generation_id`、`year`、`hour_index`|ID、Int、Int|生成版本、模型年、1—8760|
|`element_code`|Text|六元素；双向模式另保留 tieLineExport/tieLineImport；可增加派生 residualDemand|
|`energy_mwh`|Decimal|该1小时电量；1小时平均功率数值相同，单位需区分|

`residualDemand = load + tieLine − wind − solar − hydro − nonMarket`，保留负值。联络线净年电量为零时，不能删除送受两条及小时流动。288个典型小时若导出必须带 `represented_days`，全年汇总要乘月天数。

## 6. 历史现货与预测运行表

## 10. 关键约束与验收用例

### 10.1 必须由后端保证的约束

1. 各外键属于同一项目/场景，不能将甲项目的价格、乙项目电量、另一场景参数拼成合法运行。公共曲线和批次须明确访问权限。
2. 所有版本主键进入小时表唯一键；不同运行可以有同一年同一小时，不得互相覆盖。
3. 已封存配置、成功运行、粗算快照只读；重算新增版本。当前指针只在提交完整、校验成功后原子更新。
4. 页面未应用的增长率/矩阵文本不进入计算；保存草稿与提交有效配置分开。项目周期不一致需提示核对。
5. 来源、原始值、确认值和确认状态独立；改变确认状态不能连带覆盖原值或快照。
6. 总量守恒、完整时段、年表覆盖、比例边界、模型/真实日历区别均在服务端复核，不能只依赖前端校验。
7. 小时大表可按项目/运行/年组织索引或分区，但具体物理策略待容量确定。不能为优化查询删除原始版本来源。
8. 同一请求重复提交使用幂等键；并发编辑校验 `row_version`，冲突时保留双方草稿而非静默覆盖。
9. 恢复/复制项目保留原项目ID到新项目ID的来源映射和备份校验，不为满足新外键重写原粗算payload。历史快照的旧身份与新项目引用通过显式映射解释。
10. 新粗算和收益运行的头表、年度明细、摘要在提交时校验一致并一同封存。历史迁移以原备份为保真依据，结构化行按原值抽取。有差异应标记迁移校验失败并保留原对象。小时或比较缓存只从绑定版本重建。
11. 被历史引用的场景、配置、数据批次和结果走归档，禁止级联删除。物理清理依据后续确定的数据保留期限和授权范围。
12. 粗算生成若同步保存客户调整的共用参数，应在一个事务中提交配置版本、实际修改项的确认记录、输入快照和粗算结果。同次生成不改变其他默认值的待确认状态。

|T09|核对并保存同样数值|只增加确认/配置证据，不改旧粗算；后续页面不重复要求录入已确认标量|
|T10|只提高第3年费用单价10元/MWh，价量版本不变并重算|新增收益运行；第3年综合价下降10，收入下降10×该年MWh；其他年不变；原粗算hash不变|
|T11|用同一粗算与T10新旧基准分别比较|偏差变化只在第3年及全期加权汇总；比较分别绑定明确运行ID|
|T12|修改供需，或切换生效预测但不重算收益|旧运行和结果保留；清楚显示过期/旧基准状态，不把旧结果冒充新版|
|T13|粗算综合价为0或接近0|相对偏差为空，展示绝对差额；不产生Infinity或错误通过|
|T14|生成失败、导入缺行、并发保存冲突|不覆盖当前有效版本，不保存伪成功全零结果，有可定位错误|
|T15|备份后恢复历史项目，再查询导出|原始值及粗算payload hash一致；版本链、来源、确认状态、文件引用完整|
|T16|尝试跨账号访问未授权项目|服务端拒绝；前端隐藏不作为唯一安全措施|
|T17|迁移只保留归一化权重的历史典型曲线|权重及计算结果不变；原始幅值为空并标legacy_unavailable，不伪造原值|
|T18|同值确认后查看确认前的历史运行|历史确认清单仍为当时状态；当前参数显示已确认；原基准不因纯确认动作被标过期|
|T19|仅部署第3节28张物理表，用已标记的离线模拟价格完成全过程|供需清单和质量指标从宿主表读取；交叉验证展示并导出，包含两个结果ID、提示阈值和规则版本|
|T20（B）|接入同一市场时段的真实历史，切换项目容量、资产类型、配储状态|原始市场价格一致；项目捕获电价可随项目电量曲线变化|
|T21（A+）|导入覆盖全周期的外部给定价格，再生成基准收益|引用给定价格版本，显示情景来源；算法指标标不适用，时段缺项时拒绝启用|
|T22|中断一次旧项目恢复，再重试相同请求|旧备份完整；无半个新项目，重试无重复活跃对象；迁移核对报告能定位失败|

未带阶段标记的用例纳入首期。T06、T20随B验收，T21在选做A+时验收。真实模型验收另按确认后的目标、特征与评价标准编制。

验收时固定测试输入和运行版本，保留前后摘要/hash。导出价格显示6位、金额显示2位不应成为迁移截断精度规则。旧兼容算法例如 `legacy_ratio` 必须保留旧含义，不能直接按固定步长重新解释。
